# 疑难排查

## 编译器

### 「找不到编译器」/ 问题面板一直空

IDE 需要 `jhyy.exe`，查找顺序：IDE 设置里的路径 → 环境变量 `JHY_EXE` →
`../JiHuiYiYou/compiler/build/bin/jhyy.exe` → `C:\Program Files\JHYY\bin\jhyy.exe` →
`PATH` 上的 `jhyy.exe`。

最快的办法是把[编译器仓库](https://github.com/JiHuiYiYou/JiHuiYiYou-compiler)
clone 成 IDE 仓库的**兄弟目录**：

```
coding/
├── JiHuiYiYou/          ← 编译器仓库
└── JiHuiYiYou-IDE/      ← 本仓库
```

### 「gcc link failed」—— 而且一句错都没有

编译器靠 `gcc` 链接，要的是**真正的 MSYS2 UCRT64 gcc**：

- 装 MSYS2 以及 `mingw-w64-ucrt-x86_64-gcc` + `mingw-w64-ucrt-x86_64-binutils`。
- **千万别用** Git Bash 自带的 MinGW gcc
  （`C:\Program Files\Git\mingw64\bin\gcc.exe`）—— 它链不了 PE，而且**静默**失败
  （退出码 1，零字节输出）。
- `gcc` 必须以 **Windows 风格路径**能找到。只含 MSYS 风格条目
  （`/c/msys64/ucrt64/bin`）的 PATH，编译器内部 spawn 的 `cmd.exe` 不认。

### 编译器在我项目里拉了一堆垃圾

IDE 不会 —— 但它确实需要一个**可写的当前目录**，因为编译器的跨阶段临时文件走的是
**相对 CWD** 的路径（`compiler/build/obj/…`），而编译器自己不会建那个目录。
IDE 给它的是系统临时目录下的一个 scratch 目录。你要是手动在只读目录里跑
`jhyy.exe`，看到的就是这个。

## 诊断

### 问题面板里位置是空的

编译器的诊断是 stderr 上的自由文本：

```
C:\path\to\file.jhyy:12:8: error: type mismatch in let
```

正则必须**盘符感知**（`^(.*):(\d+):(\d+):`）。语言仓库 MCP server 用的
`^([^:]+):` 跨不过 `C:` 里的冒号 —— 位置会**静默**丢成空。

### 只显示一条错误

编译器**没有错误恢复**：解析器和语义分析器都在第一个错误处 bail。一次编译 ⇒
一条诊断。改掉再编。

### 编译器的进度信息混进输出了

编译成功时 stderr 也有进度噪声（`[1] imports start`、`[4] codegen done` …）。
IDE 把它们滤掉了 —— 你手动跑 `jhyy.exe` 时看到是正常的。

## 终端

### 终端是空的 / shell 根本没起来

终端是**懒启动**的：只有第一次切到**终端**页签才会拉起 shell 进程。页签一直空白的话，
看面板右边的动作按钮 —— 没有错误弹窗。最常见的原因是 shell 不在 IDE 以为的地方：
MSYS2 的 bash 在 `C:\msys64\usr\bin\bash.exe`（`ucrt64` 那个**不存在**）。

### 退格只移动光标，不删东西

那是 PowerShell 的锅。**管道下，PowerShell 的行编辑器（PSReadLine）是坏的** ——
它会把退格字节原样吐回，而行首一个退格甚至能把整个 shell 卡死。
所以 IDE **默认用 MSYS2 的 bash** —— 它的 readline 在管道下有真正的行编辑：
退格会真的擦掉、方向键能移动、历史能翻，而且**你看得见自己打的字**。

如果把终端切到 PowerShell，退格发的是 `BS (0x08)` 而不是 xterm.js 默认的
`DEL (0x7f)` —— PowerShell 认的是前者。

### 程序的输出被当命令执行了

不会再有了。IDE 以前把程序的 stdout 写进了 shell 的 **stdin**（那是*输入*）。
现在输出只进显示层。

### `vim` / `top` 这类全屏程序跑不了

**已修** —— 终端现在跑在**真 PTY** 上（`node-pty` ⇒ Windows 的 ConPTY）⇒
子进程真的觉得自己在终端上（`isatty(1)` 是 TRUE）⇒ 全屏 TUI 程序正常启动 ✓。

⚠️ `node-pty` 是**原生模块**：npm 上的预编译产物只对 **Node 的 ABI**，
Electron 得用自己的 ⇒ 必须**重新编译**，而这需要 **MSVC Build Tools**
（一次 UAC：`winget install Microsoft.VisualStudio.2022.BuildTools`）。
IDE 的 `postinstall`（`scripts/prepare-node-pty.mjs`）会自动做这个重编。

⚠️ **没装 MSVC 也不影响安装和使用** —— 会自动退回管道版（见下），
按行走的全都能用，只是全屏 TUI 跑不了。

### 终端里 `node` / `go` 找不到 —— PATH 里没有你那些工具

IDE 不是从**登录 shell** 起来的 ⇒ 它继承的是 **IDE 自己**的环境 ⇒ 你
`.bashrc` / `.bash_profile` 里加的东西（**nvm、rbenv、pyenv、conda init、
自建工具的 PATH**）一个都没有。

现在 IDE 启动时会在**后台**起一个登录 shell 把环境导出来（`env -0`）缓存住，
开终端时叠上去 ⇒ 那些工具就回来了 ✓。

⚠️ 导一次要 ~0.5-1 秒，所以是**启动时后台导**、不是开终端时现导 ⇒
**改了 `.bashrc` 要重启 IDE 才生效**。

### 终端是「假的」—— 为什么 `vim` / `top` 跑不了

**已经不是了** —— 终端跑在**真 PTY** 上（`node-pty` ⇒ Windows 的 ConPTY）⇒
子进程拿到的是**控制台设备**（`GetFileType(stdout) == 2`）⇒ `isatty(1)` 是 TRUE ⇒
全屏 TUI 程序能跑 ✓，而且窗口尺寸是**实时**的（`stty size` 跟终端对得上）✓。

后端本身是**接口**（`src/main/pty.ts` 的 `PtySession`），有两种实现：

| 后端 | 什么时候用 | 你能得到什么 |
|---|---|---|
| **node-pty（ConPTY）** | 默认（装了 MSVC） | 真控制台、TUI 程序、实时 resize、**控制台自己回显**你敲的字 |
| **管道**（`child_process.spawn`） | 兜底（没 MSVC ⇒ 编不出原生模块） | 按行走的全都能用；没有 TUI、没有实时 resize，而且 stdout 是**管道** ⇒ C 运行时**全缓冲** |

⇒ `compiler/runtime/runtime.c` 里的 `setvbuf(stdout, NULL, _IONBF, 0)`
**继续留着当兜底** ⇒ 不管跑在哪儿、stdout 是不是管道，提示都立刻可见 ✓。

### 终端里的中文输出是乱码

不该乱码 —— IDE 启动 shell 时会强制设 UTF-8，`cmd` 那边还会探测 OEM 代码页。
要是**终端**里看到乱码，先确认你不是在看一个 `cmd` 会话（它的系统消息走 OEM 代码页）。

（**输出面板**里的乱码是另一回事 —— 见下。）

### IDE 跑完程序后，终端不显示提示符了

**现在会显示了** —— 提示符会回来，而且**终端还活着**。

**以前**：IDE 用 VS Code 的**任务终端**模型跑程序 ⇒ 命令是 **shell 的启动参数**
（`bash -c "…"` / `powershell -Command "…"`）⇒ shell **跑完那条命令就退出** ⇒
⇒ 一个退了的 shell 当然不会再打提示符 ⇒ 你看到的是 IDE 自己写的那行命令
（`> jhyy compile …`），然后是编译器的输出、程序的输出 —— **没有提示符**。

**现在**：IDE 把命令**敲进你正在用的那个终端** ⇒ 程序是**那个 shell 的孩子** ⇒
⇒ 程序退出 ⇒ shell **打出提示符、继续活着** ⇒ 终端能接着用 ✓

⚠️ IDE **从来不**「向 shell 要提示符」：往 shell 的 stdin 写一个裸回车
是**一个真的回车键** ⇒ shell 会**多跑一整轮提示符** ⇒ 终端里**多一个提示符**
（见下一条）。

### 点「运行」后，终端里**一点程序输出都没有**

**症状**：点「运行」后终端里出现了那行命令，但程序的输出**一直不出现**
（有时候「运行中」还会一直亮着）。

两个原因，现在都修好了 —— 但它们能解释症状（万一你又遇到了）：

① **PowerShell 要调用运算符**。`'C:\…\prog.exe'` 在 PowerShell 里是**一个字符串**，
不是命令 ⇒ 解析器把整行拒了 ⇒ **程序压根没启动**。
（bash 那边碰巧能跑 —— 引号里有 `/` 的话 bash 会当路径执行 ⇒ **只有默认 shell 犯这个病**。）

② **pty 宿主进程压根没收到那条命令**。IDE 更愿意把真控制台放在**一个独立的辅助进程**里
（这样原生模块崩了不会把整个 IDE 带走）⇒ 那个请求必须**把命令一起带过去** ⇒
⇒ 不带的话，辅助进程起的是一个**普通的交互 shell** ⇒ **命令压根没跑**、
终端也永远不退出 ⇒ 「运行中」一直亮着。
（只有这一条路会坏 ⇒ **出不出这个毛病，取决于机器上装没装 node-pty**。）

**现在**：调用运算符加上了（`& 'C:\…\prog.exe'`），命令也传给辅助进程了 ⇒
⇒ 程序跑起来了、输出也出来了 ✓

⚠️⚠️ **bash 那边**不能**有 `&`** —— bash 的 `&` 是**后台算符** ⇒
⇒ 编译会跑到后台 ⇒ shell 立刻回提示符 ⇒ 退出码是假的、产物还没生成就去跑 ⇒ **必错** ✗
⇒ `buildShellCommand()` 已经按 shell 分好了 ✓

### 点「运行」后，终端里的程序输出被「刷新」清空了，只剩提示符

**症状**：一个终端都没有的时候点「运行」⇒ 程序跑起来了，但终端里它的输出
**忽然没了**，只剩一行 `(base) PS C:\…>` 提示符，而程序**还在跑**。

**原因**：IDE 有两条跑程序的路 ——
① 程序是 **shell 的孩子**（输出真在控制台屏幕上 ⇒ 终端重画也抹不掉）✓
② 程序跑在**自己的 pty** 里，输出靠「注入」画到终端上
⇒ ② 的输出**不在控制台屏幕里** ⇒ **控制台一重画（改终端大小）就把它抹掉** ✗

以前「一个终端都没有 ⇒ 新建的终端是**冷的**」（PowerShell 刚起、你的 profile 里
还有 conda ⇒ 第一个提示符要好几个秒才画出来）⇒ IDE 只等 **2 秒**等 shell 集成
⇒ **经常等不到** ⇒ 静悄悄走了 ② ⇒ 输出被抹掉。

**现在**：程序**永远是 shell 的孩子** ⇒
⇒ 编译器输出、程序输出、提示符**全在同一条流里** ⇒ **输出不会被抹掉** ✓
⇒ 而且**判完成靠 shell 集成报「命令执行完」** ⇒
⇒ 所以 IDE 在敲任何东西**之前**先等集成起来（⇒ 不会往一个「报不回来」的终端里写东西）✓

⇒ 万一**没有 shell 集成**（`cmd` 就是没有；或者你设了
`JHY_IDE_NO_SHELL_INTEGRATION=1`）⇒ IDE 退回**任务终端**那条路：
另开一个叫 **运行** / **检查** 的终端，命令是 shell 的启动参数 ⇒
⇒ 运行照样能用，但**那个终端跑完就死** ⇒ **降级，而且是故意让你看得见的** ✓
⇒ 你**当前的终端正忙**（你自己在跑东西）时也一样 ⇒
⇒ IDE **绝不往正忙的终端里敲东西** ⇒ 你的命令不会被搅乱 ✓

### 程序的输出后面**又出现了一遍**提示符

**症状**：程序跑完了，终端里先是一段程序输出，**紧接着又是一行 `(base) PS C:\…>`**，
像是提示符打印了两遍。

**原因**：IDE 以前有个「让 shell 重打一遍提示符」的机制 —— 它的实现是**往 shell 的
stdin 写一个裸回车**（`\r`）。那是一个**真的回车键** ⇒ shell 会**再跑一整轮提示符**
⇒ 终端里就**多一个提示符**。

更糟的是：在 **PowerShell** 里那个空回车会造一条**空的历史记录** ⇒ shell 报
「命令执行完，退出码 0」⇒ IDE 把**正在等的那次运行提前用退出码 0 收了场** ⇒
**程序的真实退出码被报成 0**。

**现在**：这个机制**整个删了** —— **shell 的提示符是唯一的提示符**
（跟 VS Code 一个模型：IDE 从来不「要」一个提示符）。
而且编译和运行是**同一条命令**（`jhyy compile "文件" && 产物`）⇒
编译器输出、程序输出、提示符**全在同一条流里** ⇒ 每条命令后面**一个**提示符 ✓。

### 关掉终端了，右上角还显示「运行中」

**症状**：程序正跑着，把那个终端关掉 ⇒ 程序还活着，界面也还显示「运行中」。

**原因**：以前**运行没有绑定到终端** —— 尤其是「没有 shell 集成」那条退路，
程序跑在**自己的 pty** 里 ⇒ 关掉终端**不会杀它** ⇒ IDE 那边等的结果**永远不来**
⇒ 「运行中」永远亮着。

**现在**：运行**绑定到终端**（VS Code 的模型：任务由**终端的 exit 事件**驱动收场）⇒
关掉终端 ⇒ **程序被杀** ⇒ 运行收场 ⇒ 状态清掉 ✓。
「运行中」那个圈在**终端页签**上（转圈 / ✓ / ✗），**不在状态栏**里 ——
底右状态栏**不显示任何程序行为**（用户明说：「右下角的状态栏戏太多了，
人家用户根本就不需要知道程序行为」）✓

### 程序不等输入就跑过去了 —— `scanf` 读不到东西

以前 IDE 给程序接的是**空设备**（stdin 直接是 EOF）⇒ 任何读 stdin 的程序
一上来就拿到 EOF ⇒ `scanf` 直接返回、程序接着往下跑。

现在程序跑在**真 PTY**（真控制台）里，IDE 把**你在终端里敲的字喂给程序** ✓
（跟 VS Code 的「在终端里运行」一个意思）—— 切到**终端**页签敲下回车，
程序就收到了 ✓。

⚠️ 字要敲在**终端**页签里（不是「输出」页 —— 那是只读的程序输出）。
敲进去的字**由控制台自己回显**（真控制台会把它收到的字符画出来，
连光标位置、宽字符都对）⇒ IDE **绝不能再回显一遍**（否则每个字出现两次）。
（管道兜底版没有 TTY ⇒ 那时由 IDE 自己回显。）

程序跑满 60 秒还没结束会被**超时杀掉**（等输入得给用户时间打字）；
疯狂打印的那种由**输出上限**（512 KB）秒杀 ✓。

### 程序的那句提示，要等我**输完**才出现

**已修** —— IDE 现在把程序跑在**真控制台**（ConPTY）里 ⇒ C 运行时对控制台的
stdout **不缓冲** ⇒ 提示**立刻**出现 ✓。

背后的道理（它解释了当初为什么会这样）是 **stdio 缓冲**：C 运行时给 stdout 的
缓冲方式取决于它是不是**交互设备**——

| stdout 是什么 | 缓冲 | `printf("请输入一个数字：")` |
|---|---|---|
| 控制台（真终端里的 `CONOUT$`） | 行缓冲 / 无缓冲 | **立刻显示** |
| 管道（CI / `jhyy run \| less` / IDE 的管道兜底） | **全缓冲**（4KB 一块） | 憋到程序退出 |

所以「在 cmd 里跑 `jhyy run` 没事，在 IDE 里跑就有事」—— 差别从来不在 jhyy，
而在**终端给程序的是控制台、IDE 给的是管道**。

⇒ 兜底也留着：修在**程序自己**的运行时里（`compiler/runtime/runtime.c` 是
每个 JHYY 程序都链进去的 C 桥）：入口加一行 `setvbuf(stdout, NULL, _IONBF, 0)`
⇒ stdout 不缓冲 ⇒ 在哪儿跑提示都立刻可见 ✓。

⚠️ 这条改动在**语言仓库**（`JiHuiYiYou`）里，不在 IDE 里 ——
IDE 只是链了那份 runtime 的编译器。

（顺带：stdout 无缓冲 ⇒ 一句话会被拆成好几段送过来，IDE 这边自己**攒行**，
所以输出面板里那行提示仍然是完整的一行 ✓）

## 窗口和外壳

### `Ctrl+C` / `Ctrl+V` / `Ctrl+Z` 没反应，或者 `F5` 把窗口重载了

那是 Electron 的**默认应用菜单**抢了 accelerator。IDE 在主进程里调
`Menu.setApplicationMenu(null)` 正是为了这个 —— 哪天把那行删了，
`F5` 就会重载整个 IDE，`Ctrl+C` 也会失灵。

### 窗口没有标题栏 / 按钮位置不对

窗口**故意没有原生边框**（`titleBarStyle: 'hidden'` + `titleBarOverlay`）：
标题栏是 IDE 自己画的，系统把最小化/最大化/关闭按钮画在它上面。
标题栏右边特意留了 ~138px 给它们。

### 编辑器打不了字 —— 看着像只读的

界面完全正常（能选中、能滚动、光标在那儿），但**一个字都打不进去**。

这是 CodeMirror 的 `indentOnInput()` 扩展在**抛异常**：它是个**事务过滤器**，
每次输入都跑 `rules.some(r => r.test(lineStart))`；而语言数据里的
`indentOnInput` 要是写成了 `true`（而不是**正则表达式**），`true.test` 就不是函数
⇒ 抛 TypeError ⇒ **整个输入事务被丢掉** ⇒ 字进不去。

规则：`languageData.indentOnInput` **必须是一个正则**（CodeMirror 文档原话：
*which must hold a regular expression*）。`tests/renderer/jhyyLanguage.test.ts`
钉着这条 —— 它直接断言「输入的事务不会抛异常」。

### 同一行里选中的字几乎看不见

两个原因叠在一起：

- **当前行的背景把选区盖住了。** `highlightActiveLine()` 给当前行加的背景是
  **行 div 自己**的 —— 而行 div 在**内容层**里，**画在选区层上面**
  （选区层的 z-index 是 -1）。不透明 ⇒ 当前行的选区被整个盖住。
  IDE 把当前行改成**半透明**了。
- **选区颜色被 CodeMirror 自带的主题盖住了。** `drawSelection()` 把**浏览器原生**的
  选区设成 transparent ⇒ 看得见的选区**只有** CodeMirror 自己画的那一层，
  而它用的是 base theme 的深蓝灰 `#222`/`#233`。IDE 的主色
  `rgba(0, 212, 170, 0.34)` 写了 `!important` 才盖得住。

### 打开 CRLF 的文件就崩（`RangeError: Selection points outside of document`）

CodeMirror 灌字符串时按 `/\r\n?|\n/` 拆行 ⇒ **`\r` 会被丢掉** ⇒
编辑器里的文档**永远是 LF**，而磁盘上的文件可能是 CRLF ⇒ 两边长度对不上 ⇒
选区被算到**文档外面** ⇒ 事务直接抛异常 ⇒ 整个编辑器崩掉。

IDE **读文件时归一化成 LF、存盘时还原原来的行尾** —— 既不崩，
也**不会把你文件的行尾改掉**。

### 「另存为」把整个文件名（连后缀一起）选中了

Windows 的保存对话框会把「文件名」框里的内容**整段选中**（含后缀）⇒ 没法只改基础名。

IDE 现在**只给目录、不给默认名** ⇒ 框是空的 ⇒ 没有「被选中的后缀」✓
（**其它一切不变**：过滤器还在，扩展名照样自动补 —— 填 "hello" ⇒ "hello.jhyy"）。

### 编辑器里 `Ctrl+V` 粘贴不了

全局快捷键在 `window` 的**捕获阶段** `preventDefault()` + `stopPropagation()`
⇒ 浏览器因此**不再触发** `paste` 事件 ⇒ 编辑器内置的粘贴处理
（CodeMirror 6 的 `handlers.paste`）永远收不到东西 ⇒ 粘不上。

规则：**编辑器/浏览器自己能处理的键，别抢**。粘贴这条命令标了 `native`
（见 `src/renderer/commands/types.ts`）⇒ 全局快捷键直接放行，让浏览器自己
派发 `paste` —— 原生路径还更快（直接读 `event.clipboardData`，不用绕 IPC）。

`tests/renderer/paste.test.ts` 钉着这条：按 Ctrl+V 时事件**不能**被
`preventDefault`。

### 新建的未命名文件，聊天里显示成「没打开文件」

未命名的新文件**没有路径**（磁盘上还不存在）⇒ 光看「有没有 filePath」
分不清「用户没开文件」和「用户开了个还没保存的新文件」。

现在聊天面板顶部的那个 chip 显示的是**文件名**（`未命名-1.jhyy`）✓，
而且 Claude 的系统提示里也会带上：文件的名字 + **用户正在编辑的内容**
（磁盘上读不到它，不给的话它只能瞎猜）✓。

### 聊天里的历史会话一直是空的

三个原因，都修了：

- `claude --resume` **只是把对话接上，不会把历史消息再吐一遍** ⇒
  历史得由 IDE 自己存、自己还原（现在历史条目里带着整段对话 ✓）。
- 而且以前**用户消息整个被忽略**了 ⇒ 就算 CLI 回吐了也进不了界面。
- sessionId **是 IDE 自己生成的**（`--session-id`），本来根本不用等 CLI 的
  `system/init` 事件 —— CLI 万一没初始化（比如模型名不被它认），那个事件永远不来。

现在：历史条目里带着整段对话（存在 localStorage ✓ 重启还在），
点一下就填回界面 ✓，同时 `--resume` 把 CLI 的上下文接上 ✓。

### 历史会话里显示的不是最终回答，而是思考过程里某句话

模型常先说一句「我先看看这个文件」（那是一条**完整**的 assistant 消息），
再调工具，最后才给最终回答。以前「显示哪段正文」的判据是
`answer ?? streaming` —— **永远优先那条旧的开场白** ⇒ 最终回答只以增量形式
到达时（有些 CLI 版本只发增量），界面上显示的还是那句开场白。

现在按**谁更新**算：增量比完整消息新 ⇒ 以增量为准 ✓。

另外，历史以前**只在「轮数变了」的时候存** ⇒ 存进去的是**还没写完**的那一轮
⇒ 恢复时看到的是半截对话。现在内容一变就（去抖后）存 ✓。

### 点历史会话要卡好几秒才连上

三个原因，都修了：

- **主进程被同步卡住**：探测「哪个 python 装了 fastmcp」用的是
  `execFileSync`（**同步**）⇒ `import fastmcp` 那几秒里**整个 IDE 都没反应**
  （用户报过「特别慢特别卡」）。现在改成异步，而且**启动时就在后台预热** ✓。
- **停旧会话死等 1.5 秒**：现在等 CLI **自己退出**（退出就立刻走）✓。
- **界面等连接完才显示**：现在**先把历史填回界面**，再去连 CLI ✓。

### 跑 `while true` 那种程序，整个 IDE 卡死

程序在无限打印，而 IDE 在**无上限地拼接**它的输出 ⇒ 内存被吃光 ⇒
机器开始换页 ⇒ 谁都动不了。

现在每个流的输出**有上限**（512 KB），超了**立刻杀掉程序**，并在状态栏说
「程序输出过多，已终止」。输出也是**边跑边显示**的（像 VS Code 的任务终端）。

VS Code 为什么不会卡？因为它跑的是**真 PTY**（Windows 上是 ConPTY）：
伪终端缓冲固定，输出比读快时**写端会阻塞**（程序自己慢下来），
xterm.js 也是边收边渲染、滚动缓冲有上限 ⇒ 内存始终有界。

**现在 IDE 也是真 PTY 了** —— 但那个上限**留着**：无限打印的程序照样能把
IDE 的内存吃光（PTY 只挡着**写端**，不挡着我们为「输出」面板留的那份）。

### 程序「崩溃」：`NTSTATUS0xC000013A`（退出码 -1073741510）

**那不是崩溃 —— 是你自己按了 Ctrl+C。**

`0xC000013A` 就是 `STATUS_CONTROL_C_EXIT`（被 Ctrl+C 终止）。现在程序跑在
**真控制台**里 ⇒ Ctrl+C 会**真的**杀掉前台程序（这正是真控制台的意义 ——
以前那个字节只是被写进管道，程序根本不知道）。

⇒ 现在 IDE 显示「**程序已中断**」，不再说「程序崩溃」✓。
（IDE 的「**停止**」按钮杀它也是这个码 ⇒ 报的是同一句话。）

### 终端一会儿真、一会儿假

**已修，而且现在**看得见**了** —— 状态栏上有个小徽章：

| 徽章 | 意思 |
|---|---|
| **PTY** | **真控制台**（ConPTY）⇒ TUI 程序能跑、窗口尺寸实时对得上、程序的提示立刻可见 |
| **管道** | **管道兜底** ⇒ 没有真 TTY。tooltip 里写着原因和该怎么办 |

以前有两件事会让终端**静悄悄**退成管道版：

1. **原生模块是懒加载的** —— `require('node-pty')` 不碰
   `build/Release/conpty.node`，**第一次 spawn 时**才碰。而 **`npm install`
   会把那个文件删掉**（node-pty 自己的 `postinstall` 会把 `build/Release`
   整个清空 —— 那是它的 bug）⇒ 现在 IDE **启动时先预热** ⇒ 模块进了 Node 的
   模块缓存 ⇒ 之后再跑 `npm install` 也**不会影响正在跑的 IDE** ✓。
2. **工作目录不存在** —— `CreateProcess` 失败、node-pty 抛异常 ⇒
   整个终端静悄悄退成管道版 ⇒ 现在 IDE 在**起进程之前**先找一个真存在的
   目录 ✓。

徽章写着「**管道**」的话，跑一次 `npm install`（`postinstall` 会按 Electron 的
ABI 重编 node-pty），然后重启 IDE。

### 终端里冒出来一堆空的提示符

**已修。** 根因是 IDE 给 shell 发命令时**行尾用了 `\r\n`** —— 那对 shell 来说是
**两个回车**（readline 的两个 accept-line）⇒ shell 打**两个**提示符、中间还夹一个
空行。换个目录就多两个空提示符，攒几次就是你看到的那一堆。

⇒ 现在行尾**按后端来**：管道用 `\n`、真控制台用 `\r`（**绝不发 `\r\n`**）。

另外两处也堵上了：

- **「补提示符」不会连着补** —— 只有 IDE 往终端里写了东西（命令回显 / 程序输出）
  之后才补一个（终端已经停在提示符上就不补）。
- **用户没在看终端时压根不补** —— 后台跑十个命令不会攒十个空提示符；
  等你切回「终端」页签时补**一个**。

## 块视图

### 块是空的 / 什么都不画

Blockly 的 `workspace.render()` 只是**排队**等下一个动画帧才画，窗口没焦点时什么都不画。
IDE 用 `Blockly.renderManagement.triggerQueuedRenders(workspace)` 强制刷。

### 块接不上

Blockly 13 里 `setNextStatement(true)` **不再建** previousConnection。
语句块必须同时调 `setPreviousStatement(true)`。而且 `<statement>` 容器装的是
**一条链** —— 连着放好几个块意味着要吐 `<next>` 元素。

### 块视图一打开就崩（`Attempt to connect incompatible types`）

Blockly 里**一个块不能既输出又前后连接**。它灌 XML 时给子块挑连接口的顺序是
**先 output、再 previous**（它分不清 `<statement>` 和 `<value>`）——
所以一个「两种位置都能用」的块（赋值 / if / match / 逃生舱）必须**拆成两个**：
语句形态（`jhyy_set`）和值形态（`jhyy_set_val`）。

反编译器要是把语句形态的块放进**表达式位置**（值输入），或者把两种形态混用，
就会撞上这个错，块视图整个崩掉。
`tests/renderer/blockWorkspace.test.ts` 把**所有样例**都灌一遍，少一个定义就红。

### 不透明块的源码丢了

每个字段都要**显式给名字**。Blockly 的 `getField('CODE')` 对没名字的字段返回 `null`，
逃生舱的载荷跟着一起丢。

### 文本视图改了，块却没动

这是设计如此：块是**切到块视图时**才重建，不是每敲一个键就重建（每键重建画布没法用）。
切一次视图就追上来了。块过期的时候 🧩 按钮上会冒个小圆点。

### 布局一变，块画布就空了 / 尺寸不对

这里有两个坑：

- **Blockly 13 没有 `ResizeObserver`。** 它只在*窗口*变尺寸时重新量。
  应用内部的布局变化（折叠聊天侧栏、打开面板、切视图）都会让画布尺寸过期 ——
  所以 IDE 自己盯着容器，调 `Blockly.svgResize(workspace)`。
- **千万别用 `display: none` 藏块面板。** `svgResize` 读的是容器的 `offsetWidth`，
  藏起来就是 0，画布会变成 0×0。IDE 改用 `visibility: hidden` + `inert` ——
  布局盒子还在。

### 动了块，源码自己变了

不该变 —— 但以前会，原因值得知道：从 XML 把块读回来时用的是 `querySelector`，
它搜的是**所有后代**。嵌套的同名输入会**遮蔽**外层的那个，
于是 `fib(n - 1) + fib(n - 2)` 读回来变成了 `fib(n - 1) + 1`。
现在每次查找都只认直接子节点（`:scope >`），`tests/renderer/blockXml.test.ts` 钉住了这条。
